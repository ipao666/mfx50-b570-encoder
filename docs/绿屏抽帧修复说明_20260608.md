# MFX50 绿屏/抽帧问题修复说明

日期：2026-06-08

## 现象

`v0009.hevc` 封装成 MP4 后仍然会绿屏闪烁。用 FFmpeg 解码原始 HEVC / remux MP4 时出现大量：

- `Could not find ref with POC ...`
- `Duplicate POC in a sequence ...`
- `non monotonically increasing dts ...`

这说明问题不只是 `.hevc` 裸流没有时间戳，也不是 MP4 容器问题，而是生成出的 HEVC 码流参考帧顺序不干净。

## 根因判断

本次检查没有发现 HybridTSRQ 自适应 QP 算法本身会直接造成这种 POC/参考帧错误。

真正风险点在实时 oneVPL pipeline：

1. 解码、编码都是异步提交。
2. 旧实现按 pipeline slot 扫描可用结果，缺少显式顺序栅栏。
3. 在 B 帧 / 长 GOP / 多 async depth 场景下，异步完成顺序可能和编码码流顺序不一致。
4. 一旦输出包顺序错位，播放器/解码器就会看到缺参考帧、重复 POC，表现为绿屏、闪屏、跳帧。

另查到一个次要问题：

`drainEncoder()` 旧逻辑只在 `syncp != nullptr` 时取 drain 阶段输出。如果 oneVPL 直接把 bitstream 写入输出 buffer 但不给 sync point，旧逻辑会跳过该输出包，可能造成尾部少帧。

## 修改内容

修改文件：

`mfx50_realtime.cpp`

改动点：

1. `PipelineOp` 增加顺序编号：
   - `decodeOrder`
   - `decodedOrder`
   - `encodeOrder`

2. `RouteContext` 增加顺序计数：
   - `nextDecodeSubmitOrder`
   - `nextDecodeOutputOrder`
   - `nextDecodedReadyOrder`
   - `nextEncodeSubmitOrder`
   - `nextEncodeOutputOrder`

3. 解码同步只处理当前应输出的最早 decode order。

4. 编码提交只选择最早 decoded order 的 surface。

5. 编码同步只输出当前应输出的最早 encode order。

6. `drainEncoder()` 增加 `syncp == nullptr && outputBs.DataLength > 0` 的直接输出处理。

## 未修改内容

没有修改 HybridTSRQ 自适应 QP 主算法：

- `temporal_qp_controller.cpp`
- `spatial_qp_controller.cpp`
- `qp_map.cpp`
- `hybridtsrq_controller.cpp`
- `mfx50rt_api.cpp`

也没有修改 QP profile、ROI/MBQP 策略、压缩率策略。

## B570 验证

验证环境：

- B570 Linux 台式机
- oneVPL + VAAPI
- `/dev/dri/renderD129`

已验证：

1. CMake Release 编译通过。
2. `ctest --output-on-failure`：13/13 通过。
3. 1080p / 30fps / 10s H.264 Annex-B 输入，`packet-mode=au`，输出 HEVC 可被 FFmpeg 无错误解码。
4. 1080p / 30fps / 10s H.264 Annex-B 输入，`packet-mode=chunk`，输出 HEVC 可被 FFmpeg 无错误解码。
5. 1080p / 30fps / 60s H.264 Annex-B 输入，`packet-mode=chunk`，输出 HEVC 可被 FFmpeg 无错误解码。

## 旧版对照验证

为了确认不是算法 QP 策略导致，本次在同一台 B570、同一份 1080p / 30fps / 60s H.264 Annex-B 输入上对照测试：

旧版源码：

`源码_干净版_20260602`

运行：

```bash
LD_LIBRARY_PATH=$PWD/build_original \
./build_original/mfx50rt_stream_probe \
  --input input_1080p_60s.h264 \
  --output original_60s_chunk_out.h265 \
  --input-kind annexb \
  --packet-mode chunk \
  --chunk-bytes 65536 \
  --codec h264 \
  --profile quality \
  --fps 30 \
  --device /dev/dri/renderD129 \
  --output-mode poll \
  --strict \
  --no-ffprobe

ffmpeg -hide_banner -v error -f hevc -r 30 \
  -i original_60s_chunk_out.h265 \
  -f null -
```

旧版 FFmpeg 解码输出复现大量：

- `PPS id out of range: 0`
- `Could not find ref with POC ...`
- `Error constructing the frame RPS.`

修复版同输入、同参数输出：

`orderfix_60s_chunk_out.h265`

FFmpeg 解码无上述 POC / RPS / PPS 错误。

这个对照说明：问题来自实时 oneVPL 异步输出顺序，和 HybridTSRQ 自适应 QP 算法本身无直接关系。

结论：

这次修的是实时 oneVPL 异步输出顺序问题。它能解释绿屏闪烁和 POC/参考帧错误；不是自适应 QP 算法本身把码流压坏。
